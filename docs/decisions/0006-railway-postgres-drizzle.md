# 0006 — Railway deploy + Railway Postgres (Drizzle) for gaps and usage ledger only

**Status:** Accepted · 2026-10-30

## Context
We need a public URL, persistence for two small tables, and request rate limiting, with minimal setup.

## Decision
Deploy the Next.js app on Railway with a Railway Postgres database. Drizzle ORM (`postgres` driver, `drizzle-kit` for migrations) defines exactly two tables: `gap_question` and `usage_ledger`. Rate limiting is an in-memory fixed window per instance.

## Consequences
- One provider for app + DB. Plain Postgres means no lock-in.
- Typed schema in `src/db/schema.ts`. Migrations generated by drizzle-kit and run explicitly (not in Phase 0).
- **Known limitation:** the in-memory rate limit resets on deploy and isn't shared across replicas. Acceptable for a single-instance prototype. With scale it moves to Postgres or Redis.
- The chat works if the DB is down. Only gap saving and ledger writes degrade.

## Alternatives
- **Vercel + a managed Postgres / KV.** Viable. Railway chosen for a long-running Node process (streaming without function time limits) and a co-located DB.
- **SQLite file.** Rejected: ephemeral filesystems on PaaS deploys.
- **Redis for rate limiting.** Deferred: another service for a prototype.
